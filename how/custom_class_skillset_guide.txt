SECTION 1: ARCHITECTURAL OVERVIEW & COMBAT LIFECYCLE

1.1 THE DEDICATED MULTI-THREADED COMBAT WORKER (SkillEngineLoop)
----------------------------------------------------------------------------------------------------
In high-end AQW combat (such as Ultra boss encounters with strict taunt and mechanic timings),
standard sequential script loops and native timer events introduce 300ms–800ms of latency per tick.

CoreDUCK bypasses this by running combat logic on a dedicated background OS thread:
- Thread Instance: `new Thread(SkillEngineLoop) { Name = "LoneWolf Skill Engine", IsBackground = true }`
- Tick Rate: Polled every `SkillPollDelay = 25ms` (or `CSSGunslingerFirePollDelay = 50ms` for specialized stances).
- Interruption Model: Preempts normal rotations immediately whenever a higher-priority action is queued.

1.2 NATIVE SKUA TIMERS VS COREDUCK BACKGROUND THREAD
----------------------------------------------------------------------------------------------------
Native Skua `Bot.Skills.Start()` relies on UI timer ticks that can freeze, drift, or skip frames during heavy
map transitions, packet floods, or window minimization.

CoreDUCK explicitly disables native skill handlers (`Bot.Skills.Stop()`) and manages all skill calls
directly via `Bot.Skills.UseSkill(index)` within its low-latency 25ms thread loop.

1.3 THE 11-TIER PRIORITY ACTION QUEUE HIERARCHY
----------------------------------------------------------------------------------------------------
Every 25ms tick, `SkillEngineLoop()` evaluates combat actions in strict descending priority order:

   +-------------------------------------------------------------------------------+
   | 1. ABSOLUTE PRIORITY TAUNT (pendingAbsolutePriorityTauntMapId)                | <-- Instant Taunt Interrupt
   +-------------------------------------------------------------------------------+
   | 2. ABSOLUTE PRIORITY SKILL (pendingAbsolutePrioritySkill)                     | <-- Forced Skill Cast (e.g. AP Seal)
   +-------------------------------------------------------------------------------+
   | 3. PENDING REGULAR / IMMEDIATE TAUNT (pendingTauntMapId / pendingImmediate)   | <-- Queued Taunt
   +-------------------------------------------------------------------------------+
   | 4. SKILL FIVE / IMMEDIATE SKILL FIVE (pendingSkillFiveMapId / Immediate)       | <-- Item/Potion/Taunt Skill 5
   +-------------------------------------------------------------------------------+
   | 5. TARGETED PRIORITY SKILL (pendingTargetedPrioritySkill)                     | <-- Switch, Cast on Add, Switch Back
   +-------------------------------------------------------------------------------+
   | 6. PRIORITY SKILL (pendingPrioritySkill)                                      | <-- Situational Heal/Cleanse
   +-------------------------------------------------------------------------------+
   | 7. LIMITED PRIORITY SKILL (pendingLimitedPrioritySkill)                       | <-- N-Counted Priority Skill
   +-------------------------------------------------------------------------------+
   | 8. CONSUMABLE AUTO-BUFF (MaintainPotion: Tonics, Elixirs, Combat Potions)    | <-- Auto-reapply on buff drop
   +-------------------------------------------------------------------------------+
   | 9. SAFE SKILL TRIGGER (SurvivalSkill when HP% < SurvivalHealthThreshold)      | <-- AUTOMATIC EMERGENCY HEAL/SHIELD
   +-------------------------------------------------------------------------------+
   | 10. CLASS-SPECIFIC SPECIALIZED ROTATION (SkillEngineMode Dispatch)            | <-- YOUR CUSTOM ENGINE
   +-------------------------------------------------------------------------------+
   | 11. FALLBACK SEQUENTIAL LOOP (CustomSkillEngine / AuraBlockedSimpleEngine)    | <-- Default 1..4 cycle
   +-------------------------------------------------------------------------------+

1.4 THE CUSTOMSKILLENGINE BASE FALLBACK LOOP
----------------------------------------------------------------------------------------------------
If no specialized logic or higher-priority action consumes the tick, `CustomSkillEngine()` executes the array
of integers defined in `preset.Skills`:
- Iterates over `skillList = GetSkillList()`.
- Checks `Bot.Skills.CanUseSkill(skill)`.
- Fires `Bot.Skills.UseSkill(skill)` on the first available skill and advances `skillIndex`.

SECTION 3: THE SAFE SKILL (SURVIVAL SKILL) PARAMETER ARCHITECTURE

3.1 PURPOSE & MOTIVATION (ELIMINATING UNNECESSARY CUSTOM ENGINES)
----------------------------------------------------------------------------------------------------
Many AQW classes have a standard builder/damage rotation (e.g. `{ 1, 4, 2 }`), but also possess a dedicated
emergency heal, cleanse, or shield skill (e.g. Skill 3 on Abyssal Angel's Shadow, or Skill 1 on Healer).

In naive bots, developers either:
1. Put the heal in `Skills = { 1, 4, 2, 3 }` -> Causes the bot to spam the heal on cooldown even at 100% HP,
   wasting mana, stealing GCD windows, and leaving the skill on cooldown when actual lethal damage hits.
2. Write a full custom 50-line state machine engine just to check `if (healthPercentage < 60) UseSkill(3)`.

The **Safe Skill** parameter provides a built-in, lightweight solution directly within `CoreDUCK`. It allows
classes running standard `SkillEngineMode.Simple` (or any mode) to have an automated, health-gated emergency
reaction without writing custom engine code!

3.2 PRESET-LEVEL CONFIGURATION (`SurvivalSkill` & `SurvivalHealthThreshold`)
----------------------------------------------------------------------------------------------------
On `ClassPreset` (`CoreDUCK.cs` ~line 6750), two integer properties control the Safe Skill mechanism:

- `public int SurvivalSkill { get; set; } = 0;`
  The skill index (1, 2, 3, or 4) that acts as the survival/healing skill. Set to `0` to disable.
- `public int SurvivalHealthThreshold { get; set; } = 0;`
  The HP percentage (1..100) below which the skill should trigger. Set to `0` to disable.

Example 1: Abyssal Angel's Shadow (`CoreDUCK.cs` line 637):
```csharp
public ClassPreset AbyssalAngelShadow(bool farmMode = false) =>

    {
        ClassName = "Abyssal Angel's Shadow",

        Skills = farmMode ? new[] { 4, 2 } : new[] { 1, 4, 2 }, // Excludes Skill 3 from regular spam!
        SkillMode = SkillEngineMode.Simple,
```

```csharp
    };
```

3.3 EXECUTION LIFECYCLE IN `SkillEngineLoop` (PRIORITY INTERCEPTION BEFORE CLASS ENGINES)
----------------------------------------------------------------------------------------------------
In `CoreDUCK.cs` (~lines 1595–1623), the Safe Skill check executes at **Priority Tier 9** during every 25ms tick:

```csharp
bool survivalSkillUsed = false;
if (
    !immediateTauntUsed
    && !skillFiveUsed
    && !immediateSkillFiveUsed
    && !targetedPrioritySkillPending
    && !prioritySkillPending
    && !limitedPrioritySkillUsed
    && !potionUsed
    && survivalSkill is >= 1 and <= 4
    && survivalHealthThreshold > 0
    && Bot.Player.Alive
    && (Bot.Player.MaxHealth > 0 && (double)Bot.Player.Health / Bot.Player.MaxHealth * 100 < survivalHealthThreshold)
)
{
    if (Bot.Skills.CanUseSkill(survivalSkill) && Bot.Skills.UseSkill(survivalSkill))
        survivalSkillUsed = true;
}

if (
    !immediateTauntUsed
    && !skillFiveUsed
    && !immediateSkillFiveUsed
    && !targetedPrioritySkillPending
    && !prioritySkillPending
    && !limitedPrioritySkillUsed
    && !potionUsed
    && !survivalSkillUsed
)
{
    // Dispatch to Class-Specific Engine or Fallback CustomSkillEngine()
    ...
}
```

Key Behavioral Properties:
1. **Interrupts Class Engines**: When HP drops below `SurvivalHealthThreshold`, the survival skill fires
   before the class specialized engine or fallback rotation runs.
2. **Preserves Normal Rotations**: When HP is healthy (above threshold), the skill is completely ignored by
   the Safe Skill check, leaving regular rotations uninterrupted.
3. **No Deadlock on Cooldown**: If the survival skill is on cooldown or out of mana, `Bot.Skills.CanUseSkill`
   evaluates to `false`, `survivalSkillUsed` remains `false`, and the loop cleanly falls through to regular
   damage skills so you never stop generating mana or attacking!

3.4 SIMPLE MODE WITH SAFE SKILL VS CUSTOM ENGINE SURVIVAL BRANCHING
----------------------------------------------------------------------------------------------------
When should you use the Safe Skill parameter vs writing a custom engine?

| Feature | Simple Mode + Safe Skill Parameter | Custom Engine Survival Branching |
|---|---|---|
| **Use Case** | Reactive heals, cleanses, shields with fixed % triggers | Complex conditional logic (mana gates, aura stack prerequisites, stance changes) |
| **Code Required** | 2 lines in `ClassPreset` (`SurvivalSkill`, `SurvivalHealthThreshold`) | Custom method + enum + dispatch case |
| **Maintenance** | Zero custom code maintenance | Full maintenance of custom state machine |
| **Examples** | `Abyssal Angel's Shadow` (Skill 3 @ 60%), `Healer` (Skill 1 @ 80%) | `King's Echo` (Skill 3 @ <50% HP AND >24% Mana, bypassed on 24 stacks) |

4.1 THREAD SAFETY & AURA LOOKUPS (PLAYER, TARGET, & TIME REMAINING)
----------------------------------------------------------------------------------------------------
AQW packet events update `Bot.Self.Auras` and `Bot.Target.Auras` continuously on the main network thread.

- INCORRECT (Thread-Unsafe):
  ```csharp
  // DO NOT DO THIS!
  // LINQ enumeration over live collections throws InvalidOperationException ("Collection was modified")
  // on background threads, causing stack evaluations to silently return 0!
  float rifts = Bot.Self.Auras.Where(a => a.Name == "Temporal Rift").Select(a => a.Value).FirstOrDefault();
  ```

- CORRECT: PLAYER AURA LOOKUP (Thread-Safe API):
  ```csharp
  // ALWAYS USE THIS:
  // Skua provides direct internal lookup methods that return aura snapshots safely.
  float rifts = Bot.Self.GetAura("Temporal Rift")?.Value ?? 0;
  ```

- CORRECT: TARGET / ENEMY DEBUFF LOOKUP (Thread-Safe API):
  ```csharp
  Aura? cocooned = Bot.Target.GetAura("Cocooned");
  ```

- CORRECT: CALCULATING AURA REMAINING TIME (Seconds Remaining):
  Skua's `Aura` object does not have a dynamic `SecondsRemaining` property; instead it provides
  `UnixTimeStamp` (epoch milliseconds when applied) and `Duration` (in seconds).
  CoreDUCK provides the thread-safe helper `GetAuraSecondsRemaining(aura)` (~line 2192):
  ```csharp
  private static double GetAuraSecondsRemaining(Aura? aura)
  {
      if (aura == null || aura.UnixTimeStamp <= 0 || aura.Duration <= 0)
          return 0;

      double remaining = (DateTimeOffset.FromUnixTimeMilliseconds(aura.UnixTimeStamp)
          .AddSeconds(aura.Duration) - DateTimeOffset.UtcNow).TotalSeconds;
      return Math.Max(0, remaining);
  }
  ```
  Example usage in custom engine:
  ```csharp
  var panicAura = Bot.Target.GetAura("Panic");
  if (panicAura == null || GetAuraSecondsRemaining(panicAura) < 1.0)
  {
      if (Bot.Skills.CanUseSkill(3) && Bot.Skills.UseSkill(3))
          return;
  }
  ```

4.2 GLOBAL COOLDOWN (GCD) DYNAMICS & THE "FAST COOLDOWN STEALING" TRAP
----------------------------------------------------------------------------------------------------
In AQW, every skill cast incurs a standard Global Cooldown (GCD ~1.0s to 1.5s).
- If your class has short-cooldown builder skills (e.g. Skill 1 with a 2.0s cooldown), checking
  `Bot.Skills.CanUseSkill(1)` inside your conditional burst block will cause Skill 1 to fire whenever
  the main burst skill (e.g. Skill 3 or 4) is on a 0.2s GCD or fraction-of-a-second delay.
- Once Skill 1 fires, it triggers *another* 1.0s GCD.
- In a continuous loop, Skill 1 and Skill 2 will perpetually steal the GCD window, preventing longer-cooldown
  or situational burst skills from ever executing.

Rule: Keep builder skills strictly inside `CustomSkillEngine()`, or ensure burst conditions require
prerequisite buffs (like Skill 3) to be cast before allowing builder strikes.

4.3 FALLTHROUGH VS DEADLOCKING (MANA & RESOURCE REGENERATION FLOW)
----------------------------------------------------------------------------------------------------
Never place an unconditional `return;` inside a conditional block if all skills in that block might be
on cooldown or waiting for mana:

- Deadlock Pattern (Broken):
  ```csharp
  if (temporalRift >= 4)
  {
      if (Bot.Skills.CanUseSkill(3) && Bot.Skills.UseSkill(3)) return;
      if (Bot.Skills.CanUseSkill(4) && Bot.Skills.UseSkill(4)) return;
      return; // <-- DEADLOCK! Halts all attacks, stops auto-attacks, freezes mana regen forever!
  }
  ```

- Clean Fallthrough Pattern (Working):
  ```csharp
  if (temporalRift >= 4)
  {
      if (Bot.Skills.CanUseSkill(3) && Bot.Skills.UseSkill(3)) return;
      if (Bot.Skills.CanUseSkill(4) && Bot.Skills.UseSkill(4)) return;
  }

  // Fall through to CustomSkillEngine() so auto-attacks and builders continue generating mana!
  CustomSkillEngine();
  ```

4.4 BURST SEQUENCING & MULTI-SKILL SUCCESSION (3 -> 1 -> 4 ROTATIONS)
----------------------------------------------------------------------------------------------------
For chronomancers and multi-step burst classes:
- Sequence skills in decreasing order of prerequisite dependency: Buffs (Skill 3) -> Prep (Skill 1) -> Nuke (Skill 4).
- When a skill successfully fires, return immediately (`return;`) to yield the 25ms tick, allow the packet
  to register, and let the GCD run its course before the next step evaluates.

4.5 MULTI-MODE CLASS ARCHITECTURE (DEFAULT VS SOLO / SPECIALIZED STANCES)
----------------------------------------------------------------------------------------------------
When a class has two distinct playstyles (e.g. Arachnomancer Group/Ravenous vs Solo/Dauntless, or
LightCaster DPS vs Healing, or Chrono ShadowHunter Stable vs Gunslinger):
1. Give the factory method a boolean parameter with a safe default:
   `public ClassPreset Arachnomancer(bool soloMode = false) => ...`
2. Define distinct modes or enhancement profiles for each branch:
   - When `soloMode == true`: return `SkillMode = SkillEngineMode.ArachnomancerSolo`, `WeaponSpecial.Dauntless`, etc.
   - When `soloMode == false`: return `SkillMode = SkillEngineMode.Simple`, `WeaponSpecial.Ravenous`, etc.
3. In `GetClassPreset(string className)`: return the standard/default variant.
4. In `TestClassDUCK.cs`: expose a dropdown enum so the user can easily test either mode.

5.1 REFERENCE 1: THE KING'S ECHO PATTERN (Threshold Nuke + Internal Survival Branching)

```csharp
public void KingsEchoSkillEngine(bool useSurvivalSkill)
{
    if (!Bot.Player.Alive)
    {
        skillIndex = 0;
        return;
    }

    if (!Bot.Player.HasTarget || Bot.Player.Target?.HP <= 0)
        return;

    float residualEnergy = Bot.Self.GetAura("Residual Energy")?.Value ?? 0;

    // 1. Prioritize Nuke (Skill 4) when stacks reach 24 or mana is low

        (residualEnergy >= 24 || Bot.Player.Mana < kingsEchoManaThreshold)

        : 0;
    double manaPercentage = Bot.Player.MaxMana > 0
        ? (double)Bot.Player.Mana / Bot.Player.MaxMana * 100
        : 0;

        useSurvivalSkill
        && healthPercentage < 50
        && manaPercentage > 24
        && Bot.Skills.CanUseSkill(3)
        && Bot.Skills.UseSkill(3)
    )
        return;

    CustomSkillEngine();
}
```

SECTION 6: SCRIPT OPTIONS & SKUA COMPILER CONVENTIONS (`TestClassDUCK.cs`)
====================================================================================================

6.1 THE FIRST-TYPE DISCOVERY RULE (`assembly.GetExportedTypes().FirstOrDefault()`)
----------------------------------------------------------------------------------------------------
When Skua compiles a `.cs` script file and prepares its script configuration (`LoadScriptConfig`),
it discovers the script instance using:
```csharp
assembly.GetExportedTypes().FirstOrDefault()
```
- The primary script class (e.g. `public class TestClassDUCK`) **MUST** be the very first type declared
  in the file directly following the `using` statements.
- Never declare `enum` or helper class types at file scope *above* the script class. If you do, Skua will
  instantiate the enum, find no `public List<IOption> Options` field on it, and show the error:
  `"The loaded script has no options to configure."`
- Always declare custom enums nested *inside* the script class or at the very bottom of the file.

6.2 SUPPRESSING UNSKIPPABLE LAUNCHER POPUPS (`DontPreconfigure = true`)
----------------------------------------------------------------------------------------------------
- In Skua, if a script sets `public bool DontPreconfigure = false;`, Skua's native launcher hooks into
  the "Start Script" button and unconditionally displays the options modal *before* `ScriptMain()` runs.
  Crucially, Skua's native hook **does not check `SkipOptions`**.
- Standard scripts (like `0AllUltras_LW.cs` and `TestClassDUCK.cs`) declare:
  ```csharp
  public bool DontPreconfigure = true;
  ```
  This suppresses Skua's unskippable launcher popup, allowing `Core.SetOptions()` in `ScriptMain()`
  to honor the `SkipOptions` ("Skip this window next time") checkbox properly!

6.3 DISABLING AUTOMATIC LAG KILLER IN TESTING SCRIPTS (`Core.AntiLag = false`)
----------------------------------------------------------------------------------------------------
- In `CoreBots.cs`, `public bool AntiLag { get; set; } = true;` defaults to `true`.
- When `Core.SetOptions()` runs, it checks `if (AntiLag)` and forces `Bot.Options.LagKiller = true`,
  while freezing monster positions and hiding all combat animations.
- For combat testing scripts (`TestClassDUCK.cs`), always set:
  ```csharp
  Core.AntiLag = false;
  Core.SetOptions();
  Bot.Options.LagKiller = false;
  ```
  This ensures that damage numbers, animations, and monster models remain fully visible during testing.

6.4 WIRING MULTI-MODE DROPDOWNS INTO SCRIPT OPTIONS
----------------------------------------------------------------------------------------------------
To let the user select between different stances/modes in `TestClassDUCK.cs`:
1. Nest the enum inside the class:
   ```csharp
   public class TestClassDUCK
   {
       public enum ArachnomancerMode { Solo_Dauntless, Default_Ravenous }
       ...
   ```
2. Add an `Option<T>` to `Options`:
   ```csharp
   new Option<ArachnomancerMode>(
       "ArachnomancerMode",
       "Arachnomancer Mode",
       "Solo (Dauntless) or Default (Ravenous).",
       ArachnomancerMode.Solo_Dauntless
   ),
   ```
3. Read the option in `ResolvePreset()`:
   ```csharp
   var mode = Bot.Config?.Get<ArachnomancerMode>("ArachnomancerMode") ?? ArachnomancerMode.Solo_Dauntless;
   return Duck.Arachnomancer(soloMode: mode == ArachnomancerMode.Solo_Dauntless);
   ```
