1. EXECUTIVE SUMMARY & OVERVIEW
================================================================================
"0AllUltras_LW.cs" (All Ultras LoneWolf) is the master orchestrator script in the
LoneWolf (LW) Ultra combat framework for Skua / AdventureQuest Worlds (AQW).

Its primary objective is to autonomously coordinate a 4-player party (Army)
across 11 high-difficulty "Ultra" boss encounters (4 Daily Ultras + 7 Weekly
Ultras) in a single uninterrupted automated gauntlet run.

Key Operational Highlights:
---------------------------
- Multi-Process IPC: Skua client instances run in separate Windows processes.
  0AllUltras_LW and CoreLoneWolf synchronize all accounts via atomic, file-based
  Inter-Process Communication (IPC) text files (.sync) stored in Skua Options.
- Upfront Party Consensus: Before entering any combat zone, all 4 accounts cast
  an upfront ballot checking which quests they still need. If an Ultra is already
  completed on all 4 accounts, the entire party skips that boss seamlessly.
- State Cleansing (Oracle Reset): AQW retains lingering combat auras, debuffs,
  and state locks across room transitions. Between Ultra fights, the orchestrator
  teleports accounts to their house and equips the Oracle class to purge all
  auras and reset ability cooldowns cleanly.
- Modular Delegation: Rather than hardcoding 11 boss fights into one giant file,
  0AllUltras_LW acts as a controller that dynamically executes standalone boss
  classes (e.g., UltraSpeaker_LW, UltraEzrajal_LW) via the unified interface
  method "RunFromMaster()".

3.1 Configuration & MultiOptions Storage
----------------------------------------
0AllUltras_LW uses Skua's MultiOptions configuration format to present a
clean, structured GUI tab layout:
- Category "Setup":
  * player1..player4: Account usernames (Player 1 is the leader/sync boss).
  * PrivateRoomNumber: Room instance number (1001 to 99999).
  * UseEnhancements (bool): Auto-applies Forge & optimal enhancements.

- Category "Weekly_Ultras":

3.3 The Upfront Distributed Quest Ballot (BuildPartyRequiredMask)
-----------------------------------------------------------------
When "SkipCompletedUltras" is enabled, the script executes a ballot before
fighting any boss:
1. LoneWolf.StartArmySync("0AllUltras_Completion.sync", 4, "Setup") initializes
   the sync session.
2. Each client checks its local quest status:
   `NeedsUltra(category, optionName, questId) => enabled && !IsDailyComplete(id)`
3. For every needed Ultra, the client calls `LoneWolf.SendArmySignal("ULTRA_REQUIRED_<bit>")`.
4. The army calls `LoneWolf.SyncArmy("COMPLETION_MASK_READY")` to ensure all 4
   accounts have submitted their signals.
5. Each client iterates through the sync log. If ANY player (1 to 4) emitted
   the signal for bit X, that bit is added into `partyRequiredMask`.

3.4 Dynamic Run Mask Resolution
-------------------------------
`actualRunMask = skipCompletedUltras ? (selectedMask & partyRequiredMask) : selectedMask;`
`remainingUltras = CountUltras(actualRunMask);`
If `actualRunMask == 0`, all requested Ultras are completed and the script
exits immediately with no unnecessary room hops.

3.5 The Oracle Aura Reset Protocol (PrepareOracle & ResetBetweenUltras)
-----------------------------------------------------------------------
In AQW, high-end boss mechanics apply permanent or long-duration combat auras
(e.g., Focus, Sanctity, Righteous Seal, Mana Lock, Noxious Decay, Liberator).
Changing rooms normally does NOT clear these auras from the player entity,
which causes premature wipes on subsequent boss attempts.

To solve this:
1. `PrepareOracle()`:
   - Verifies if the account owns the "Oracle" class.
   - If not in inventory, opens Bank, searches for "Oracle", and moves to inventory.
   - If not in bank, visits `/join classhalla-99999` and purchases Oracle (ID 759).
2. `ResetBetweenUltras()` (executed after every successful Ultra fight if more remain):
   - Sends `%xt%zm%house%1%<Username>%` to warp directly into the player's house.
   - Waits for map load.
   - Equips "Oracle". Swapping classes forces AQW's client and server combat
     managers to wipe all active auras, debuffs, and state flags.
   - Sleeps 1,000ms to allow packet settlement before proceeding to the next boss.

3.6 Master-to-Slave Sequential Execution Pipeline
-------------------------------------------------
The script evaluates bosses in strict, deterministic order:
Ezrajal -> Warden -> Engineer -> Tyndarius -> Drakath -> Drago -> Nulgath
-> Dage -> Darkon -> Gramiel -> Speaker.

For each boss:
```csharp
RunSelectedUltra("Daily_Ultras", "RunUltraEzrajal", "Ultra Ezrajal", EzrajalBit,
                 () => new UltraEzrajal_LW().RunFromMaster());
```
Inside `RunFromMaster()`:
1. `masterMode = true` tells the child script to read configuration from
   `0AllUltras_LW`'s multi-category storage instead of standalone options.
2. The child script starts its own dedicated `.sync` session (e.g. `UltraEzrajal_LW.sync`).
3. Validates level & weapon requirements, accepts quest, enhances gear, drinks
   potions, and runs up to `MaxFightAttempts` (3 attempts).
4. Returns `UltraRunResult`:
   - `UltraRunResult.Completed`: Quest turned in successfully. Advances queue.
   - `UltraRunResult.AttemptsExhausted`: 3 attempts failed. Logs warning and
     advances to the next Ultra so the gauntlet is not blocked.
   - `UltraRunResult.Failed` (or stopped by user): Halts entire sequence.

4. THE CORELONEWOLF IPC PROTOCOL & CROSS-CLIENT SYNCHRONIZATION
================================================================================

4.1 File Transport Architecture & Path Resolution
-------------------------------------------------
Because each Skua client is an independent OS process, cross-account
communication cannot use shared memory pointers.
CoreLoneWolf implements a flat-file IPC transport stored at:
`%AppData%\Roaming\Skua\Options\<syncFileName>`

File I/O Safety Measures:
- Multi-Process File Sharing: Opened with `FileMode.Append`, `FileAccess.Write`,
  and `FileShare.Read` to allow multiple processes to append concurrently.
- Retry Loop: If a process encounters an `IOException` (file lock contention),
  it sleeps `ArmyFileRetryDelay` (100ms) and retries automatically.
- Sanitization: All record fields are validated via `IsSafeArmyField()` to
  prevent pipe delimiter injection or newline corruption.

4.2 Wire Protocol Grammar & Record Formats
------------------------------------------
Every line written to a `.sync` file follows a pipe-delimited format:
`<RECORD_TYPE>|<PROTOCOL_VERSION>|<SESSION_ID>|<PARAM_1>|...|<PARAM_N>`

The Protocol Version is fixed to `"1"`.

Standard Records:
-----------------
1. `RESET|1|<sessionId>`
   - Emitted by `playerOne` (Leader) at startup to invalidate all previous sessions.
2. `READY|1|<sessionId>|<username>|<launchToken>`
   - Emitted by each player (1..4) advertising readiness with a unique GUID token.
3. `START|1|<sessionId>|<token1>|<token2>|<token3>|<token4>`
   - Emitted by `playerOne` after receiving `READY` tokens from all 4 players.
     Locks the army roster into this session.
4. `STEP|1|<sessionId>|<stepId>|<stepName>`
   - Emitted by `playerOne` to initiate a synchronization barrier (e.g. `SETUP_DONE`,
     `FIGHT_READY`, `START_FIGHT`, `BOSS_DEFEATED`, `FINISH`).
5. `ARRIVED|1|<sessionId>|<stepId>|<username>`
   - Emitted by each player when they reach the checkpoint designated by `stepId`.
6. `CONTINUE|1|<sessionId>|<stepId>`
   - Emitted by `playerOne` once all 4 players have logged `ARRIVED` for `stepId`.
     Releases followers from the barrier.
7. `SIGNAL|1|<sessionId>|<signalName>|<username>`
   - Asynchronous broadcast signal (e.g. `ULTRA_REQUIRED_1`, `FIGHT_DEAD_1`,
     `FIGHT_ALIVE_1`, `RIGHTEOUS_SEAL_READY_1`).
8. `STOP|1|<sessionId>|<reason>`
   - Emitted by `playerOne` to signal session termination (`COMPLETE`,
     `ATTEMPTS_EXHAUSTED`, or fatal error).

4.3 Leader (playerOne) vs Follower (playerTwo..playerFour) State Machine
-----------------------------------------------------------------------

    +-------------------+                       +-------------------+
    |    PLAYER ONE     |                       |   PLAYER TWO..N   |
    |     (Leader)      |                       |    (Followers)    |
    +-------------------+                       +-------------------+
              |                                           |
     Emits RESET & READY                         Emits READY (Token)
              |                                           |
     Waits for all Tokens                                 |
              |                                           |
     Emits START (All Tokens) --------------------------> Detects START
              |                                           |
     Emits STEP (stepId, name) -------------------------> Detects STEP
              |                                           |
     Emits ARRIVED                               Emits ARRIVED
              |                                           |
     Waits for all ARRIVED                                |
              |                                           |
     Emits CONTINUE ------------------------------------> Detects CONTINUE
              |                                           |
     [Executes Task]                             [Executes Task]

4.4 Token Exchange, Session Validation & Desync Recovery
--------------------------------------------------------
- Launch Tokens: Every client generates a random GUID (`armyLaunchToken`) on
  `StartArmySync()`.
- Roster Lockdown: `playerOne` includes all 4 tokens in the `START` record. If a
  stale client from a previous run attempts to write, its token mismatch causes
  it to be ignored.
- Replaced Sessions: If a client reads a `RESET` record with a newer `sessionId`,
  it detects that the leader restarted the army, terminates its current run,
  and logs `"Army sync session was replaced"`.

4.5 Distributed Death Tracking & Wipe Consensus (ShouldResetFight)
------------------------------------------------------------------
During combat, accounts constantly monitor party health via `ShouldResetFight()`:
1. If an account dies, it appends `SIGNAL|1|<session>|FIGHT_DEAD_<attempt>|<username>`.
2. When it respawns, it appends `SIGNAL|1|<session>|FIGHT_ALIVE_<attempt>|<username>`.
3. Each client scans the recent signals. If 2 or more players are dead simultaneously
   (`deadCount >= deadPlayerThreshold`), the fight is declared unsalvageable.
4. `playerOne` emits `FIGHT_RESET_<attempt>`.
5. All 4 accounts stop attacking, kill their skill engines, jump to `SafeCell`,
   and sync at `FIGHT_RESET_<attempt>_SAFE` before retrying.

5. THE LOW-LATENCY MULTI-THREADED COMBAT & SKILL ENGINE
================================================================================

5.1 Dedicated Skill Thread (100ms Tick) vs Native Skua Skill Timers
-------------------------------------------------------------------
Skua's built-in `Bot.Skills.Start()` relies on GUI timer loops and script-level
function evaluation which introduces 300ms - 800ms of latency per skill cast.
In Ultra boss fights where a taunt missed by 0.5s causes a total team wipe,
this latency is fatal.

CoreLoneWolf completely bypasses native skill timers:
- Calls `ValidateFunctionBasedSkillsDisabled()` to ensure Skua timer is off.
- Spawns a dedicated background thread: `new Thread(SkillEngineWorker)` with
  `IsBackground = true`.
- Ticks at `SkillPollDelay = 100ms` (and `CSSGunslingerFirePollDelay = 50ms` for
  Chrono Shadowhunter burst windows).

5.2 Priority Action Queue Hierarchy
-----------------------------------
The `SkillEngineWorker` evaluates actions in strict priority order every 100ms:

1. Absolute Priority Taunt (`pendingAbsolutePriorityTauntMapId`):
   - Highest priority. Immediately interrupts normal rotations to cast
     `Scroll of Enrage` (Skill 5/Item) on the specified monster map ID.
2. Immediate Taunt (`pendingImmediateTauntMapId`):
   - Casts Enrage immediately if off cooldown, returning true/false.
3. Pending Regular Taunt (`pendingTauntMapId`):
   - Queues taunt to fire on the very next available GCD/animation frame.
4. Absolute Priority Skill (`pendingAbsolutePrioritySkill`):
   - Forces an immediate class skill cast (e.g. AP Skill 4 `Righteous Seal`).
5. Priority Skill (`pendingPrioritySkill`):
   - High-priority situational skill cast (e.g. emergency heal or cleanse).
6. Targeted Priority Skill (`pendingTargetedPrioritySkill`):
   - Targets a specific add/monster, casts the skill, and targets back.
7. Class-Specific Specialized Rotations:
   - Executes specialized mode logic (KingsEcho, ArcanaInvoker, etc.).
8. Standard Sequential Skill Loop (`skillList` index progression).

5.3 Consumables Subsystem (Tonics, Elixirs, Combat Potions, Scrolls)
-------------------------------------------------------------------
`PreparePotions()` and `PrepareScrolls()` fully automate inventory preparation:
- Potion Categories:
  * Tonic: Fate Tonic (Luck), Sage Tonic (Int), Body Tonic (End).
  * Elixir: Potent Battle Elixir (Physical), Potent Malevolence Elixir (Magical),
    Potent Revitalize Elixir (HoT).
  * Combat Potion: Potent Honor Potion (+dmg), Felicitous Philtre (+crit dmg).
- Automatic Purchasing & Banking:
  * Checks inventory -> checks bank and unbanks -> joins `/alchemyacademy` (Shop 2036)
    and purchases with gold if missing.
- Scroll Crafting:
  * Scrolls of Enrage (Quest 2330), Decay (Quest 2331), Mystify (Quest 2344).
  * If below threshold (80 for Enrage, 10 for Decay/Mystify), visits `/spellcraft`
    (Shops 693 & 549), buys Arcane Quills and Spell Inks, and turns in quests.
- Combat Maintenance (`MaintainPotion`):
  * Skill engine tracks potion auras. If Tonic/Elixir buff drops, re-casts from
    inventory.

5.4 Forge Enhancement Optimizer & Automated Fallback Trees
----------------------------------------------------------
`PrepareEnhancements()` configures optimal Forge weapon, helm, and cape
enhancements, with automated fallback chains if high-tier Forge items are not
unlocked on the account:

Example Fallback Chains:
- Weapon (Arcana's Concerto) -> Ravenous -> Valiance -> Praxis -> Health Vamp.
- Weapon (Elysium)           -> Valiance -> Awe (Health Vamp / Mana Vamp).
- Cape (Vainglory)           -> Lament -> Absolution -> Forge -> Regular Cape.
- Helm (Forge / Vim / Examen)-> Anima -> Base Enhancement (Lucky / Wizard).

5.5 Specialized Class Combat Engines
------------------------------------
CoreLoneWolf includes dedicated state-machine skill engines for complex classes:
- Kings Echo (`SkillEngineMode.KingsEcho`):
  * Monitors player mana against `kingsEchoManaThreshold = 12`.
  * Suppresses high-cost damage abilities when mana drops, reserving mana strictly
    for survival skills and taunts.
- Arcana Invoker (`SkillEngineMode.ArcanaInvoker`):
  * Tracks tarot card cycles ("0 - The Fool", "Judgement Day", "XXI - The World").
  * Automatically handles card cycling and aligns the World nuke.
- Chrono Shadowhunter (`SkillEngineMode.ChronoShadowHunterGunslinger`):
  * Tracks "Gunslinger Stance" and "Rounds Empty" auras.
  * Ticks at 50ms polling rate during burst window to unleash maximum damage.
- Shaman (`SkillEngineMode.Shaman`):
  * Maintains "Elemental Embrace" aura, manages Skill 3 toggles to avoid mana lock.
- LightCaster Healing Mode (`SkillEngineMode.LightCasterHealing`):
  * Replaces damage skills with prioritized heal rotations during heal checks.

6. FLASH PACKET DETECTION & REAL-TIME EVENT SNIFFING
================================================================================

6.1 Packet Sniffer Architecture (PacketDetectorThread)
------------------------------------------------------
Certain Ultra mechanics execute within 1.0s of a visual or chat tell from the
boss. Polling boss HP or player auras is too slow.

CoreLoneWolf implements a Flash Packet Sniffer:
- `StartPacketDetector(string[] commands, string[] texts)`:
  Attaches to Skua's low-level packet handler (`Bot.Events.ExtensionPacketReceived`
  and `Bot.Events.PacketReceived`).
- Intercepts raw server-to-client JSON/XML packets before Skua UI processes them.
- Increments `packetDetectionCount` and stores `packetSelectedPacket`.
- Allows Ultra scripts to call `HasPacketDetection(count)` to react within
  single-digit milliseconds.

6.2 Packet Patterns, Boss Markers & Animation String Parsing
------------------------------------------------------------
Common Packet Signatures Intercepted:
- Dage Decay Warning: Chat command `ct` with text:
  `"I possess the full power of the Legion at my disposal."`
- Speaker Truth / Listen Cues:
  `"I will make you see the truth."` / `"You shall listen."`
- Darkon Attack Animations: Packet text contains:
  `"\"animStr\":\"Attack2\""` or `"\"animStr\":\"Attack3\""`
- Gramiel Phase 2 Attacks: Packet text contains:
  `"\"animStr\":\"Charge\""`, `"\"animStr\":\"Charge2\""`, `"\"animStr\":\"ChargeAttack2\""`,
  or `"Liberator"`.
- Nulgath Abyss Summon: Chat packet containing `"Abyss!"`.

9. ERROR HANDLING, FAIL-SAFES & RESILIENCY
================================================================================

1. Automated Quest Prerequisite Bypass:
   - In `ValidateUltraAccess()`, if an account has not completed the prerequisite
     story quest (e.g. "The Engineer" 8151 or "Your Hero" 9125), the engine calls
     `Bot.Quests.UpdateQuest(prereqId)` to bypass the lock and enable the Ultra.
2. Weapon Damage Requirement Verification:
   - Scans equipped weapons to ensure >= 30% damage boost. Emits alert if missing.
3. Death & Desync Recovery:
   - If an account dies during combat, `RecoverFromDeath()` monitors respawn,
     jumps back to `BossCell,BossPad`, re-establishes target lock, and re-attaches
     to the Skill Engine.
4. Wipe Threshold Consensus:
   - If 2 players die, `ShouldResetFight()` triggers a coordinated retreat to
     `SafeCell`, cleanses combat state, and retries up to 3 times before failing
     safely to prevent endless death loops.
5. Post-Run Oracle Aura Purge:
   - Warps to player house and equips Oracle class between boss fights to ensure
     zero lingering debuffs or aura locks carried over into the next encounter.
